## Gate 1 — Current architecture

- `QuizStartService` selects questions and `QuizStartSessionWriter` installs the active quiz in PHP session keys `quiz_session`, `questions`, `answers`, `currentQuestion`, and exam review state. `QuizStartSessionPayloadFactory` sets a server deadline for timed exams. The selected question objects in the PHP session contain answer keys; the quiz view renders question text and choices, while scoring reads the session objects.
- `QuizFlowController` routes exam actions. Batch 739 binds POST forms to the current `quiz_session.id`. `QuizSubmissionService` validates answers and stores them in the session. Navigation and review marks are also session-backed.
- `ExamTimerService` enforces `deadline_epoch` before learner actions and invokes the existing finalization path when the server deadline has elapsed. It never trusts the browser clock to extend time.
- `QuizResultService` scores from the session question/answer arrays. `QuizResultPersistenceService` writes a completed record through `AttemptService`; `AttemptService` assigns `LearnerIdentityService::current()` and makes same-owner `session_id` saves idempotent. Results become durable only at finalization.
- `LearnerIdentityService` gives anonymous learners a random identity stored in the PHP session. Cookie/session loss makes that identity unrecoverable. Authenticated account learners have a stable server-issued `account-learner-*` identity checked by `AccountSessionService` against account status and `auth_version`.
- Accounts are experimental: `AccountFeatureGate` is always false for `APP_ENV=production`, otherwise requires `BOARDPREP_ACCOUNTS_ENABLED=true`; account routes are registered only in nonproduction. Product-readiness marks public account activation P1/partial pending independent review, owner/privacy decisions, and verified hosting/session/backup operations. Batch 740 will not change that gate.
- `App::storage()` supports JSON collections and SQLite-backed collections. The existing `attempts` collection is completed-result history and is already part of account export, encrypted backup, and deletion. There is no durable active-exam draft collection or attempt recovery endpoint.
- Account sign-in rotates the PHP session ID and CSRF token. It keeps anonymous quiz state in a separate pending-anonymous scope; it does not link guest attempts to an account.

## Gate 2 — Threat model and scope decision

PASS for an opt-in, nonproduction, authenticated-account implementation only. Production account enablement remains unavailable and is not part of this batch. Guests remain session-backed and cannot recover after PHP session loss.

- Recovery will resolve the owner from `AccountSessionService::current()`. Request parameters, attempt identifiers, quiz identifiers, browser storage, and recovery URLs will not supply identity or authorize access. Foreign drafts will produce the same response as no draft.
- Account IDs and learner IDs are server-issued and checked against the active account record and auth version. Login rotates the PHP session and CSRF token; cookie security remains deployment-dependent and public account routes remain disabled in production.
- Recovery and draft mutations will require CSRF and the current quiz-session binding. A durable revision plus a server-side active-session binding will reject stale forms and stale recovered sessions. An identical already-persisted answer may be acknowledged as an idempotent retry; a conflicting stale write will not overwrite current state.
- Draft operations will serialize with account lifecycle/deletion through `AccountLifecycleLock`, enforce one active draft per verified learner, and use JSON/SQLite storage records. Account ownership is checked on every read and write. A draft ID is opaque but never treated as an authorization credential.
- Durable records will contain selected canonical question IDs and the learner's validated answers, never correct answers or explanations. Recovery will rehydrate questions from the current canonical repository and reject missing/ineligible question IDs. Result views remain gated on server finalization. No answer data will be stored in browser storage.
- The existing absolute server deadline is copied without recomputation. Expiry follows the current server policy: saved responses are finalized on the next authenticated request. Expired records cannot reopen. Finalization keeps the existing same-owner session-idempotency path and removes the draft after the result record exists.
- No owner identity exists for a guest after PHP session loss. Guest recovery by knowing a quiz/draft ID would be unsafe, so it is explicitly unsupported. Account deletion must remove owned drafts; export/backup may contain only the safe learner-answer draft fields and no answer keys or active session authorization values.
- JSON storage rewrites a collection atomically; SQLite uses the existing `storage_records` abstraction. A separate draft collection avoids rewriting the larger completed `attempts` collection. One active draft per account bounds per-account active storage. Finalized drafts are deleted; timed expiry is applied when the learner returns. Untimed drafts remain until explicit completion, abandonment, or account deletion because no existing retention policy authorizes a new expiry period.

The remaining public-account P1 is a release/operational gate, not permission to enable this preview feature in production. If the opt-in prototype cannot preserve the stated invariants on both local backends, implementation stops at that gate.

## Gate 3 — Draft model and compatibility plan

Proposed isolated `exam-drafts` collection, separate from completed `attempts`: schema version, opaque draft ID, verified `user_id`, stable idempotency/draft reference, current quiz-session binding, ordered question IDs, validated answer map, current position/review marks, immutable exam configuration, original `deadline_epoch`, draft revision, and timestamps/state. Do not persist question bodies, correct answers, explanations, credentials, CSRF values, or PHP session IDs.

The JSON backend will use `APP_STORAGE_PATH/exam-drafts.json`; SQLite will route the same collection through existing `storage_records`. Missing collections are treated as empty. The migration importer, backup/package exclusions, account inventory/export/backup/restore/deletion definitions, and synthetic fixtures must be updated together. Existing completed-attempt records and anonymous data remain unchanged. A failed/corrupt draft read fails closed and does not overwrite existing storage. Recovery after a canonical question is removed or becomes ineligible is unavailable rather than silently replacing the question.

No schema change or migration of existing result records is planned. An older binary ignores the new optional collection; a newer binary sees an absent collection as empty. Downgrading while drafts exist makes them temporarily unavailable; the file/SQLite rows must be preserved for a later compatible binary. This is a known rollback limitation, not a destructive cleanup instruction.
